# SOSD querying program

SOSD 데이터셋(정렬된 정수 키 배열)에서 주어진 키의 위치를 빠르게 찾는 프로그램입니다.

- 검색 결과: 키가 처음 등장하는 위치(0부터 시작), 없으면 "데이터셋에 없음"
- 성능 = 빌드 시간 + 있는 키 검색 시간 + 없는 키 검색 시간
- 제약: 싱글 스레드, 메모리 512MB (Windows Job object)

## 빌드 / 실행

1. `team_project/team_project.slnx`를 Visual Studio 2022 이상으로 엽니다.
2. 구성을 **Release | x64**로 놓고 빌드합니다. 800MB 파일을 매핑해야 하므로 x86에서는 동작하지 않습니다.
3. 데이터 파일(예: `uniform_dense_200M_uint32`)을 `team_project/team_project/data/`에 넣습니다.
   데이터 파일은 용량이 커서 저장소에 올리지 않습니다.

```
team_project.exe [데이터파일] [--index] [--step N] [--bench] [--queries N] [--u32|--u64]
```

| 실행 예 | 설명 |
|---|---|
| `team_project.exe` | 기본 파일(`data/uniform_dense_200M_uint32`)로 대화형 검색 (보간 탐색) |
| `team_project.exe data/uniform_sparse_200M_uint32` | sparse 데이터로 대화형 검색 |
| `team_project.exe --index --step 4096` | 보간 탐색 대신 SosdIndex(샘플 인덱스)로 검색 |
| `team_project.exe data/uniform_dense_200M_uint32 --bench --queries 10` | 모든 방법 비교 벤치마크를 실행하고 `result.txt`에 추가 |

대화형 모드에서는 정수 키를 입력하면 위치와 검색 시간이 출력됩니다. `q`를 입력하면 종료되고, 빌드·검색 시간 합계가 출력됩니다.

## 설계

점수는 **빌드 시간 + 검색 시간**입니다.
검색 1회는 1µs 안팎이라 쿼리 수가 많지 않으면 **빌드 비용이 전체를 좌우합니다**.
그래서 기본 방법은 빌드가 사실상 없는 보간 탐색입니다.

### 1. 메모리 매핑 파일 (`mapped_file.*`)
200M개 × 4B = 800MB라서 512MB 제한 안에서는 데이터를 통째로 메모리에 올릴 수 없습니다.
그래서 파일을 읽기 전용으로 메모리 매핑합니다.
- 파일 매핑은 Job object가 제한하는 커밋 메모리에 포함되지 않습니다.
- 실제로 접근한 4KB 페이지만 OS가 읽어 옵니다.
- 따라서 빌드할 때 파일 전체를 읽을 필요가 없습니다.

### 2. 보간 탐색 + 적응형 위치 캐시 — 기본 방법 (`interp_search.h`)
dense와 sparse 모두 같은 알고리즘을 씁니다.
균등 분포 데이터는 위치를 `(key - min) / (max - min) * n`으로 거의 정확하게 예측할 수 있습니다.
- **빌드**: 파일 매핑과 최솟값·최댓값 읽기뿐입니다. 약 0.01ms가 걸립니다.
- **검색 비용의 대부분은 page fault입니다.** 처음 접근하는 4KB 페이지를 OS가 가져오는 비용입니다.
  전체 min/max로 한 예측은 정답에서 수천 칸 떨어져서 쿼리당 페이지를 2~3개 건드립니다.
- **적응형 위치 캐시 (adaptive indexing)**
  - 검색하면서 이미 읽은 (위치, 키) 쌍을 키의 상위 비트 기준 4096개 버킷에 기록합니다.
  - 다음 쿼리는 근처 버킷에 기록된 점을 보간의 양 끝점으로 씁니다.
  - 캐시를 채우려고 데이터를 추가로 읽지 않습니다. 그래서 쿼리가 적어도 손해가 없고, 쿼리가 쌓일수록 예측이 정답 페이지에 바로 떨어집니다.
- **가드 프로브**: 예측 위치 p를 확인한 뒤 p±32도 확인해서 구간의 양 끝을 함께 좁힙니다. 같은 페이지 안이라 추가 비용이 거의 없습니다.
- **이진 탐색 fallback**: 보간 한 번에 구간이 절반 이하로 줄지 않으면 다음 단계는 이진 탐색을 합니다. 그래서 분포가 치우친 데이터에서도 최악 O(log n)이 보장됩니다.
- 참고 논문: Van Sandt et al., *Efficiently Searching In-Memory Sorted Arrays: Revenge of the Interpolation Search*, SIGMOD 2019

개선 과정 비교입니다. 같은 실행 안에서 번갈아 7회씩 측정한 중앙값(ms)이고, uniform_dense 기준입니다(sparse도 거의 같음).

| 쿼리 수 (hit+miss 각각) | 전역 보간 | 지연 구간 캐시 | **적응형 캐시 (최종)** |
|---|---:|---:|---:|
| 10 | 0.069 | 0.075 | **0.065** |
| 1,000 | 6.0 | 5.8 | **4.7** |
| 10,000 | 53.5 | 34.2 | **34.1** |
| 100,000 | 224.0 | 180.0 | 191.1 |

### 3. 3단계 인덱스 — 비교용 (`sosd_index.h`, `--index`)
| 단계 | 자료구조 | 역할 |
|---|---|---|
| 1 | Radix 테이블 | 키의 상위 비트로 샘플 구간을 바로 찾음 |
| 2 | 샘플 배열 (희소 인덱스) | `step`개마다 키 1개를 저장하고 구간 안에서 이진 탐색 |
| 3 | 원본 데이터 블록 | 보간 예측 → 지수 탐색 → 이진 탐색 |

- 쿼리당 시간은 가장 짧습니다(약 0.15µs).
- 대신 빌드할 때 샘플마다 파일 페이지를 하나씩 건드려야 해서 수 ms에서 수십 ms가 걸립니다.
  OS 캐시에 없는 첫 실행이라면 디스크 랜덤 읽기 수천 번이 됩니다.
- 쿼리가 수만 개 이상일 때만 보간 탐색보다 유리합니다.

### 4. 비교 기준 (`baseline.h`)
- `ifstream` 이진 탐색: 탐색 단계마다 `seekg` + `read`
- 메모리 매핑 배열 전체에 `std::lower_bound`

## 참고 측정값 (WSL2 Linux, 직접 생성한 균등 분포 200M uint32)

빌드 + hit 검색 + miss 검색 합계(ms)입니다.

| 방법 | 쿼리 10+10개 | 쿼리 1만+1만 개 |
|---|---:|---:|
| ifstream 이진 탐색 | 0.94 | 427 |
| mmap 이진 탐색 | 0.35 | 27.5 |
| **보간 탐색 (기본)** | **0.08** | 21.5 |
| SosdIndex step=4096 | 16.9 | 19.9 |
| SosdIndex step=65536 | 4.8 | 18.0 |

실제 제출 환경(Windows)에서는 `--bench`로 다시 측정해야 합니다.
OS 페이지 캐시 상태(첫 실행인지 반복 실행인지)에 따라 값이 크게 달라집니다.
