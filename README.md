# SOSD 검색 프로그램 (전체 로드 방식 / 오프셋 방식)

## 파일 구성

| 파일 | 내용 |
|---|---|
| `common.h` | 공통 코드: 오프셋 지정 파일 읽기, 메모리 맵, 시간 측정, 512MB 메모리 제한(Job Object), 쿼리 입력 처리 |
| `full_load.cpp` | **전체 로드 + 버킷 인덱스** 방식 |
| `offset_search.cpp` | **오프셋 직접 접근 + 희소 인덱스 + 보간 탐색** 방식 (`--mmap` 옵션으로 메모리 맵 사용) |
| `gen_queries.cpp` | 테스트용 쿼리 파일 생성기 (있는 키와 없는 키를 섞어서 생성) |
| `CMakeLists.txt` | Visual Studio 2022에서 바로 여는 용도 |

---

## 1. Visual Studio 2022에서 빌드하기

### 방법 A: CMake 폴더 열기 (가장 간단)
1. Visual Studio 2022 → **파일 → 열기 → 폴더** → 이 폴더 선택
2. 위쪽 구성 드롭다운에서 **x64-Release** 선택 (없으면 "구성 관리"에서 추가)
3. **빌드 → 모두 빌드**

### 방법 B: 일반 콘솔 프로젝트
프로그램마다 프로젝트를 하나씩 만들어요. `full_load.cpp` + `common.h`, `offset_search.cpp` + `common.h` 이런 식으로 넣으면 돼요.
프로젝트 속성에서 아래를 꼭 설정하세요.
- 구성: **Release**, 플랫폼: **x64** (Debug는 10배 이상 느리고, x86은 메모리를 400MB 이상 잡기 어려워요)
- C/C++ → 언어 → C++ 언어 표준: **ISO C++17**
- C/C++ → 명령줄 → 추가 옵션: **`/utf-8`** (한글 주석 때문에 필요)
- C/C++ → 최적화: **최대 속도 (/O2)**

## 2. 실행 방법

```
full_load.exe      <데이터셋 파일> [-q] [--limit512]
offset_search.exe  <데이터셋 파일> [-q] [--mmap] [--limit512]
gen_queries.exe    <데이터셋 파일> <쿼리 개수> <출력 파일> [있는 키 비율=0.5] [seed=42]
```

| 옵션 | 의미 |
|---|---|
| `-q` | 쿼리마다 결과를 출력하지 않고 요약만 출력 (배치 모드) |
| `--limit512` | Job Object로 이 프로세스의 메모리를 512MB로 제한 |
| `--mmap` | (offset_search만) ReadFile 대신 메모리 맵 파일 사용 |

### 대화형 모드 (키를 직접 입력)
```
full_load.exe uniform_sparse_200M_uint32 --limit512
key> 123456789
  position 5748301  (0.210 us)
key> 5
  not found     (0.150 us)
```
끝낼 때는 **Ctrl+Z 입력 후 Enter**를 누르면 빌드 시간, 검색 시간, 총시간이 출력돼요.

### 배치 모드 (쿼리 파일 리다이렉트)
```
gen_queries.exe uniform_sparse_200M_uint32 10000 q10k.txt
offset_search.exe uniform_sparse_200M_uint32 -q --limit512 < q10k.txt
```
입력 파싱 시간은 측정에서 빠져요. 모든 쿼리를 먼저 읽어 둔 뒤 검색 구간만 측정해요.

### 출력 형식
- 위치는 **0부터** 셉니다. 1부터 세야 하면 `common.h`의 `POSITION_BASE`를 1로 바꾸세요.
- 같은 키가 여러 개면 **처음 등장하는 위치**를 출력해요.
- 없는 키는 `-1`(배치 모드) 또는 `not found`(대화형 모드)로 출력돼요.
- uint32 범위(0~4294967295)를 벗어난 입력은 바로 "없음"으로 처리해요.

## 3. 두 방식의 동작 원리

### 전체 로드 + 버킷 인덱스 (`full_load`)
- 키를 `(키 − 최소키)`로 바꾼 뒤 **상위 비트 = 버킷 번호**, **하위 shift 비트 = 저장값**으로 나눠요.
  - `start[b]` : 버킷 b의 첫 키 위치 (uint32 배열)
  - `low[i]` : i번째 키의 하위 비트 (키당 1바이트)
- 상위 비트는 버킷 번호로 이미 알 수 있으니 저장하지 않아요. 그래서 원본 800MB가 **약 300~330MB**로 줄어요.
- shift는 데이터 범위를 보고 자동으로 정해요.
  - sparse: 7비트, 버킷 3,355만 개, 버킷당 평균 약 6개
  - dense: 3비트, 버킷 2,500만 개, 버킷당 평균 약 8개
- **빌드**: 파일을 한 번만 순차로 읽어요 (16MB씩).
  - 1단계: 키마다 `start[버킷+1] = 위치+1`을 조건 없이 기록해요.
  - 2단계: 빈 버킷을 앞 값으로 채워요 (누적 최대값).
  - 분기가 없는 방식이라 처음 만든 버전보다 sparse 빌드가 약 2배 빨라졌어요 (0.95초 → 0.45초).
- **탐색**: 버킷 번호 계산 → `start` 두 칸 읽기 → 버킷 안 6~8개 확인. 사실상 O(1)이에요.

### 오프셋 + 희소 인덱스 + 보간 탐색 (`offset_search`)
- i번째 키의 파일 오프셋은 `8 + 4×i`예요. 그래서 파일 자체를 "디스크 위 정렬 배열"로 써요.
- **빌드**: 헤더와 일정 간격 샘플 257개만 읽어 희소 인덱스를 만들어요. 수 ms면 끝나요.
- **탐색**:
  1. 희소 인덱스에서 키가 속한 구간을 찾아요.
  2. 보간으로 위치를 추정해요.
  3. 그 위치의 4KB 블록(키 1,024개)을 가져와 메모리에서 이진 탐색해요.
  4. 블록 밖이면 범위를 좁혀 다시 보간해요. 4번 넘게 반복되면 이분 탐색으로 바꿔서 최악의 경우에도 O(log n)을 보장해요.
- 실측 결과 쿼리 1개당 블록 접근은 **dense 약 0.72회, sparse 약 1.26회**예요.
- ReadFile 방식은 최근 블록 1,024개(4MB)를 캐시에 보관해요.

## 4. 측정 결과 (참고용)

측정 환경은 클라우드 리눅스 VM(2코어, 가상 SSD)이고, 키 2억 개짜리 합성 데이터를 썼어요. SOSD와 같은 형식이지만 실제 SOSD 파일은 아니에요. **실제 Windows PC에서는 숫자가 달라지니 꼭 직접 다시 측정하세요.** 정확성은 numpy 전수 비교로 모든 경우 일치를 확인했어요. 경계값, 중복 키, 범위 밖 입력도 포함했어요.

**총시간(빌드 + 검색), 단위: 초.** cold는 OS 파일 캐시를 비운 직후, warm은 파일이 이미 OS 캐시에 있는 상태예요.

| 데이터 | 쿼리 수 | 캐시 | full_load | offset (ReadFile) | offset (--mmap) |
|---|---|---|---|---|---|
| dense | 100 | cold | 0.693 | **0.010** | 0.011 |
| dense | 1만 | cold | 0.544 | **0.270** | 0.268 |
| dense | 100만 | cold | **0.735** | 8.13 | 7.38 |
| sparse | 100 | cold | 0.993 | **0.015** | 0.016 |
| sparse | 1만 | cold | 0.507 | **0.455** | 0.457 |
| sparse | 100만 | cold | **0.716** | 9.02 | 7.95 |
| dense | 100 | warm | 0.982 | 0.0024 | **0.0004** |
| dense | 1만 | warm | 0.608 | 0.0097 | **0.0031** |
| dense | 100만 | warm | 0.516 | 0.785 | **0.260** |
| sparse | 100 | warm | 0.532 | 0.0021 | **0.0015** |
| sparse | 1만 | warm | 0.599 | **0.018** | 0.026 |
| sparse | 100만 | warm | 0.696 | 1.587 | **0.491** |

쿼리 1개당 탐색 시간은 이래요.
- full_load: 약 0.06~0.12µs
- offset cold: 약 25~50µs (디스크 읽기)
- offset warm: ReadFile 약 0.8~1.6µs, mmap 약 0.26~0.5µs

**손익분기점 (이 환경 기준)**
- 캐시가 비어 있을 때: 약 **1만~2만 개**
- 캐시가 차 있을 때 (ReadFile): 약 **40만~60만 개**
- 캐시가 차 있을 때 (mmap): **100만 개에서도 오프셋 방식이 빠름**

## 5. 주의할 점

1. **mmap과 메모리 제한**
   - Job Object의 메모리 제한은 *커밋(private) 메모리* 기준이에요. 그래서 `--mmap`은 제한에 거의 걸리지 않아요 (실측 private 약 3MB).
   - 하지만 쿼리가 많으면 *작업 집합(working set)*에는 읽은 파일 페이지가 잡혀서 600MB 이상으로 보일 수 있어요.
   - 조교님이 메모리를 어떤 값으로 재는지 확인하고 쓰세요. 애매하면 ReadFile 방식이 안전해요.
2. **cold 측정 방법 (Windows)**
   - 같은 파일로 두 번째 실행부터는 OS 캐시 때문에 빨라져요.
   - 캐시를 비우려면 Sysinternals **RAMMap → Empty → Empty Standby List**를 쓰거나 재부팅하세요.
   - 보고서에는 cold와 warm을 나눠서 쓰는 게 좋아요.
3. **평가 쿼리 수 확인**: 쿼리가 수천 개 이하면 offset이, 수십만 개 이상이면 full_load가 유리해요(cold 기준). 조교님께 쿼리 수와 입력 방식을 꼭 확인하세요.
4. **튜닝 값**
   - `offset_search.cpp`: `SAMPLE_COUNT`(희소 인덱스 크기), `CACHE_SLOTS`(블록 캐시)
   - `full_load.cpp`: `START_BUDGET`(버킷 표 크기 상한)
   - 이 값들을 바꿔 가며 측정하면 보고서의 실험 내용으로 쓰기 좋아요.
5. 멀티스레딩은 쓰지 않았어요 (과제 조건).
